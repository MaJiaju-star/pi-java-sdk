# 错误处理、安全与反压

## 异常类型

所有 SDK 异常都继承自 `PiClientException`（`RuntimeException`）：

```
PiClientException
├─ PiRpcException              PI 返回 success: false
├─ PiRequestTimeoutException   请求在配置时间内没有响应
├─ PiProcessException          子进程启动/退出/stdin 写入失败
└─ PiProtocolException         stdout 非法 UTF-8、JSONL 或响应关联失败
```

| 异常 | 触发条件 | 关键字段 |
| --- | --- | --- |
| `PiRpcException` | PI 返回 `success: false` | `command()` 失败的命令名 |
| `PiRequestTimeoutException` | 请求超时 | `command()`、`timeout()` |
| `PiProcessException` | 进程启动失败、异常退出、stdin 写入失败 | `exitCode()`（可空）、`stderr()` |
| `PiProtocolException` | stdout 非法 UTF-8、非法 JSONL、响应无法关联 | — |

`PiProcessException` 会把非空 stderr 附加到异常消息；`exitCode()` 在进程未退出或无法取得时为 `null`。

> 实验性 `pi-java-remote` 模块另有两个异常 `PiRemoteServerException`（远程服务端结构化错误）和 `PiRemoteException`（CBOR/传输/握手/协议失败），属于远程协议，不在本仓库的 `exception` 包内。

### 子进程启动失败的排查

`PiClient.start()` 失败时，异常类型取决于失败阶段：

| 异常 | 含义 | 先查什么 |
| --- | --- | --- |
| `IOException`（如 `CreateProcess error=2`） | **可执行文件找不到**，由 `ProcessBuilder.start()` 直接抛出，**不是** `PiClientException` | `PATH`、`executable(...)` / `command(...)` 配置、Windows 是否漏了 `.cmd` 后缀 |
| `PiProcessException`「等待 PI RPC 启动超时」 | 进程已启动，但 `startupTimeout` 内没回应 `get_state` | `node` 是否在 `PATH` 中、PI 凭据是否配好，以及 `stderr()` |
| `PiProcessException`「PI RPC 启动失败」 | 就绪探测返回了错误 | `getCause()` 与 `stderr()` |

排查建议：

1. 先用 `PiCliVersion.detect(config)` 单独验证命令能否执行（它执行 `pi --version` 并返回原始输出）。
2. 再打开 `stderrConsumer(System.err::print)`，让子进程的报错直接可见。
3. 完整路径解析规则与常见失败对照表见 [02-客户端配置与生命周期 — PI 可执行文件路径解析](02-客户端配置与生命周期.md#pi-可执行文件路径解析)。

## 异步异常传播

异步 API 的异常在 `CompletableFuture` 中传播：

- 调用 `join()` 时通常包裹为 `CompletionException`；
- 调用 `get()` 时通常包裹为 `ExecutionException`；
- 用 `whenComplete` / `exceptionally` 可拿到根因。

```java
client.getState().whenComplete((state, error) -> {
    if (error != null) {
        Throwable cause = error instanceof CompletionException ce ? ce.getCause() : error;
        System.out.println(cause.getClass().getSimpleName());
    }
});
```

同步抛出的异常（如 `prompt()` 在上一轮未结束时抛 `IllegalStateException`、参数为 `null` 抛 `NullPointerException`）直接抛出，不进 future。

## 超时

默认 RPC 响应超时为 5 分钟（`requestTimeout` 默认值，见 [02-客户端配置与生命周期](02-客户端配置与生命周期.md)）：

```java
PiClientConfig.builder().requestTimeout(Duration.ofMinutes(2));
client.request("custom_command", Map.of(), Duration.ofSeconds(30));
```

- 单次请求可用带 `timeout` 的 `request(...)` 重载覆盖默认值。
- 请求超时**不会自动中止** PI 正在进行的模型或 Bash 操作。需要停止副作用时同时调用 `abort()` 或 `abortBash()`。

## 事件反压

监听器运行在独立事件分发虚拟线程，不直接占用 stdout 解析线程。缓冲区默认容纳 1024 个事件（`eventBufferCapacity`）。

`PiEventOverflowStrategy` 四种策略：

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| `BLOCK` | 阻塞读取并通过操作系统管道向 PI 反压，不丢事件 | 默认、审计和完整 UI |
| `DROP_OLDEST` | 丢弃缓冲区中最旧事件 | 只关心最新进度的界面 |
| `DROP_LATEST` | 丢弃新到达事件 | 保留先到事件的诊断流程 |
| `FAIL` | 缓冲区满时使客户端失败并终止 PI 子进程 | 不能接受丢失或阻塞的严格系统 |

> 丢弃策略可能丢失 Extension UI 请求，不适用于需要扩展交互的宿主；此时应使用 `BLOCK` 或 `FAIL`。

## 安全边界

`workingDirectory` 不是沙箱。PI 默认工具（`read`、`write`、`edit`、`bash`）可以读写文件并执行 Bash。服务端至少应实施：

- 每个租户独立目录或容器。
- 模型凭据不返回浏览器、不写入事件日志。
- 限制图片、prompt、JSONL、CBOR 帧和进程数量。
- 对 Extension UI 回复做会话归属检查。
- 审计工具调用，限制危险命令和网络出口。

> 「限制危险命令」不能靠订阅事件实现——工具事件（`tool_execution_start` 等）只是事后通知，`abort()` 也只是竞态。真正的强制点在 PI 扩展的 `tool_call` 钩子（可 `block`、可改参数），再经 Extension UI 子协议把决策权交给 Java，见 [08-Extension-UI](08-Extension-UI.md)。

详细部署建议见 [16-Solon多用户部署与模型凭证](16-Solon多用户部署与模型凭证.md)。
