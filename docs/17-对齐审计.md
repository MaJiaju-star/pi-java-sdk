# 对齐审计：Java SDK vs TypeScript RPC

本文记录 `pi-java-sdk` 与 PI 源码中 RPC 子进程集成（TypeScript 侧 `runRpcMode`）的协议对齐情况。审计基于本地 PI 源码 **0.85.1** 与 Java SDK 当前源码逐文件比对。

## 结论

**协议表面对齐程度 100%**：RPC 命令 33/33、流式事件 25/25、Extension UI 方法 9/9、UI 响应 3/3、`get_state` 响应字段 12/12。差异只存在于「工程能力」和「同进程 SDK 边界」，不属于 RPC 协议缺口。

## 审计范围

| 侧 | 比对文件 |
| --- | --- |
| TypeScript（协议定义方） | `packages/coding-agent/src/modes/rpc/rpc-types.ts`、`rpc-mode.ts`、`../core/agent-session.ts`、`packages/agent/src/types.ts` |
| Java（客户端实现） | `PiRpcCommand`、`PiEventType`、`PiTypedEvent`、`PiRpcTypes`、`PiExtensionUiRequest`、`PiExtensionUiResponse`、`PiClient` |

## RPC 命令：33/33

TS 的 `RpcCommand` 联合类型定义 33 个命令，与 Java `PiRpcCommand` 枚举一一对应，且 Java 为每个命令都提供了强类型专用方法（`PiClient` 上），并非只有通用 `request()`。命令分组与可选参数（`parentSession`、`since`、`outputPath`、`customInstructions`、`streamingBehavior`、`excludeFromContext`）两侧一致。

## 流式事件：25/25

TS 侧 stdout 输出 = `AgentSessionEvent`（23 种）+ 单独发出的 `extension_ui_request` + `extension_error` = 25 种。Java `PiEventType` 枚举 25 种（不含 `UNKNOWN`），`PiTypedEvent` 为每种提供强类型 record 视图，未知事件保留原始 JSON。

细节：TS 的 `summarization_retry_attempt_start` 是判别联合（`source: "branchSummary" | "compaction"`），Java 的 `SummarizationRetry` record 保留 `source` + `reason` 字段完整捕获。

## Extension UI：9/9 方法 + 3/3 响应

方法：`select` `confirm` `input` `editor` `notify` `setStatus` `setWidget` `setTitle` `set_editor_text` 全部对应，Java 另有 `UNKNOWN` 兜底与 `expectsResponse()`、`timeout()` 辅助。响应三态 `value` / `confirmed` / `cancelled` 两侧一致。

## 响应数据对齐

`get_state` 的 12 个字段逐项一致（`model`、`thinkingLevel`、`isStreaming`、`isCompacting`、`steeringMode`、`followUpMode`、`sessionFile`、`sessionId`、`sessionName`、`autoCompactionEnabled`、`messageCount`、`pendingMessageCount`）。其余响应 record（`Model`、`ModelCycle`、`CompactionResult`、`BashResult`、`SessionStats` 等）使用 `@JsonIgnoreProperties(ignoreUnknown = true)` 与 `JsonNode` 兜底，向前兼容。

## 差异点（非协议缺口）

### Java 独有的工程能力

- `PiClientPool`：多会话进程池 + `recover()` 故障恢复（TS 的 `rpc-client.ts` 是单连接测试用客户端，无池）。
- `PiCliVersion.detect()`：CLI 版本探测与 `isTestedVersion()`。
- 事件反压显式化：`eventBufferCapacity` + `PiEventOverflowStrategy` 配置项。

### API 形态差异（已在本次补齐）

| 项 | 原状态 | 处理 |
| --- | --- | --- |
| `bash(String)` 单参重载 | 缺失（TS 的 `excludeFromContext` 可选） | 已补，默认 `false` |
| `prompt(String, PiStreamingBehavior)` 重载 | 缺失（TS 允许无图带 streamingBehavior） | 已补 |

### 语义一致性说明

- `prompt` 完成语义：TS 的 response 只在 preflight 成功后发出（≈ accepted），结束靠 `agent_settled` 事件；Java 的 `PiRun.accepted()` ≈ preflight 成功、`PiRun.settled()` ≈ `agent_settled`。两侧一致，表达方式不同。
- `set_model` 找不到模型：TS 服务端返回 `success: false`，Java 侧映射为 `PiRpcException`。语义一致，异常类型不同。

### 边界（TS SDK 独有，Java 不提供，属设计边界）

`createAgentSession()` 同进程嵌入（Provider 直连、Agent 内核、扩展运行时、TUI 组件）是 Node.js 内部 SDK，不是 RPC 子进程集成的一部分，Java 明确不复制（见 `docs/13-API覆盖与兼容性.md`）。

## 漂移检查机制

`PiRpcCommandCoverageTest` 读取 `../../packages/coding-agent/src/modes/rpc/rpc-types.ts`，断言 Java `PiRpcCommand` 命令集与协议定义相等。该测试用 `Assumptions.assumeTrue(Files.exists(...))` 保护，只有目录布局满足时才运行。

### 启用方式

测试期望 PI monorepo 的 `packages/` 位于 Java 仓库的上两级目录。例如 Java 仓库在 `D:\code\PI\pi-java-sdk`，则需要 `D:\code\packages` 指向 monorepo 的 `packages`：

```powershell
New-Item -ItemType Junction -Path D:\code\packages `
  -Target D:\code\PI\PI-source\pi-0.85.1\packages
```

已在本机创建该 Junction，漂移检查现随 `mvn test` 实际运行并通过（`Skipped: 0`）。PI 升级新增/删除命令时，Java 构建会自动失败，提示同步 SDK。
