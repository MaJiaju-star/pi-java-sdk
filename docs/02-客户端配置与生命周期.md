# 客户端配置与生命周期

## 进程关系

一个 `PiClient` 对应一个 `pi --mode rpc` 子进程和一个活动 PI 会话。`PiClient` 线程安全，但不要在多个业务用户之间共享同一个客户端：流式事件没有 prompt 请求 ID，无法安全拆分给多个并发调用者。多用户场景应使用 `PiClientPool`（见 [09-会话池与故障恢复](09-会话池与故障恢复.md)）。

## 启动配置

```java
PiClientConfig config = PiClientConfig.builder()
        .executable("pi.cmd")
        .workingDirectory(Path.of("D:/workspace/project"))
        .provider("openai")
        .model("gpt-5.4")
        .sessionName("代码审查")
        .sessionDirectory(Path.of("D:/pi-sessions"))
        .noSession(false)
        .environment("OPENAI_API_KEY", token)
        .startupTimeout(Duration.ofSeconds(20))
        .requestTimeout(Duration.ofMinutes(5))
        .shutdownTimeout(Duration.ofSeconds(3))
        .build();
```

`PiClientConfig` 构建后不可变，集合属性在构建时复制，可安全地在多线程间共享。

## 配置项与默认值

| 方法 | 默认值 | 作用 |
| --- | --- | --- |
| `executable` | Windows `pi.cmd`，其他 `pi` | 指定 PI 可执行文件 |
| `command(List<String>)` | — | 指定完整启动前缀，例如 `List.of("node", "D:/cli.js")` |
| `workingDirectory` | 当前目录 | PI 工具操作的工作目录，**不是安全沙箱**；会转为绝对路径并规范化 |
| `environment(name, value)` | 空 | 追加或覆盖子进程环境变量 |
| `argument(String)` | 空 | 追加原始 PI CLI 参数 |
| `argument(name, value)` | 空 | 追加名称与值分离的参数（作为两个独立 argv 项） |
| `provider` | — | 等价 `argument("--provider", provider)` |
| `model` | — | 等价 `argument("--model", model)` |
| `sessionName` | — | 等价 `argument("--name", name)` |
| `sessionDirectory` | — | 等价 `argument("--session-dir", 绝对路径)` |
| `noSession(boolean)` | 不追加 | 为 `true` 时追加 `--no-session` |
| `startupTimeout` | 15 秒 | `get_state` 就绪探测超时 |
| `shutdownTimeout` | 3 秒 | 正常关闭与强制关闭各自等待的最长时间 |
| `requestTimeout` | 5 分钟 | 单个 RPC 请求等待响应的默认最长时间 |
| `maxJsonLineBytes` | 16 MiB（16777216） | 单条 JSONL 的字节上限，不能小于 1024 |
| `maxCapturedStderrChars` | 64 KiB（65536） | 内存中保留的 stderr 尾部字符数，0 表示不保留 |
| `eventBufferCapacity` | 1024 | 等待业务监听器消费的最大事件数，必须大于 0 |
| `eventOverflowStrategy` | `BLOCK` | 事件缓冲区满时的处理方式 |
| `stderrConsumer` | 空操作 | stderr 增量文本回调，在专用虚拟线程中执行 |
| `listenerErrorHandler` | `Throwable::printStackTrace` | 事件监听器异常处理器 |

SDK 自动追加 `--mode rpc`，`command` 中不要重复填写。

## PI 可执行文件路径解析

### 默认行为

不配置 `executable` / `command` 时，SDK 使用**裸可执行文件名**，交给操作系统的 `PATH` 解析（`PiClientConfig.defaultPiExecutable()`）：

| 平台 | 默认命令 |
| --- | --- |
| Windows | `pi.cmd` |
| macOS / Linux | `pi` |

也就是说，只要 `pi` 能从 `PATH` 找到，`PiClient.start()` 开箱即用，**不需要配置任何路径**。SDK 不会主动猜测 PI 的安装位置。

### Windows 必须带 `.cmd` 后缀

Windows 的 `CreateProcess` **不做 `PATHEXT` 补全**——这与在 CMD 里敲 `pi` 会自动命中 `pi.cmd` 不同。实测：

| 作为 `argv[0]` 传入 | 结果 |
| --- | --- |
| `pi.cmd` | ✅ 启动成功 |
| `C:\Users\<用户>\AppData\Roaming\npm\pi.cmd` | ✅ 启动成功 |
| `pi` | ❌ `CreateProcess error=2, 系统找不到指定的文件` |

所以 Windows 上 `executable("pi")` 会失败，必须写 `executable("pi.cmd")`；反过来，macOS / Linux 上写 `pi.cmd` 也会失败。

### 三种配置方式

```java
// 1) 默认：什么都不配，依赖 PATH
PiClient client = PiClient.start();

// 2) 指定可执行文件（替换整个命令前缀）
PiClientConfig.builder()
        .executable("C:\\Users\\Administrator\\AppData\\Roaming\\npm\\pi.cmd")
        .build();

// 3) 指定完整命令前缀（SDK 会在末尾追加 --mode rpc 与 arguments()）
PiClientConfig.builder()
        .command(List.of("node", "C:/path/to/coding-agent/dist/bundle/cli.js"))
        .build();
```

`executable(x)` 等价于 `command(List.of(x))`，两者互相覆盖（后设置的生效）；区别只在于 `command(...)` 可以表达带参数的多段命令。

### 底层机制

```java
List<String> commandLine = new ArrayList<>(config.command());
commandLine.add("--mode");
commandLine.add("rpc");
commandLine.addAll(config.arguments());

ProcessBuilder processBuilder = new ProcessBuilder(commandLine)
        .directory(config.workingDirectory().toFile());
processBuilder.environment().putAll(config.environment());
Process process = processBuilder.start();
```

要点：

- **不经过 shell**。`ProcessBuilder` 直接把 argv 交给 `CreateProcess` / `execve`，不会有引号、通配符或变量展开。Windows 上 JDK 内部会为 `.cmd` / `.bat` 自动包一层 `cmd.exe /c`，所以裸名 `pi.cmd` 能正常执行。
- **环境变量是「继承 + 覆盖」**，不是替换。`environment(name, value)` 只改动指定项，其余继承自当前 Java 进程。
- **`workingDirectory` 是 PI 子进程的当前目录**，不是安全沙箱（见 [12-错误处理安全与反压](12-错误处理安全与反压.md#安全边界)）。

### 常见失败原因

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `CreateProcess error=2` / `No such file or directory` | `PATH` 中找不到 PI | 用 `executable(...)` / `command(...)` 写绝对路径 |
| 命令行里能跑，IDE / Windows 服务 / Docker / CI 里启动失败 | Java 进程的 `PATH` 与交互式终端不同 | 同上，不要依赖 `PATH` |
| `pi.cmd` 启动后立刻退出，stderr 报找不到 `node` | `pi.cmd` 是 npm 生成的包装脚本，内部仍要调用 `node` | 确保 `node` 也在 `PATH` 中，或改用 `command(List.of("node", "cli.js"))` |
| 启动成功但 `.pi/extensions/` 下的扩展没加载 | `workingDirectory` 不是预期目录，PI 相对当前目录发现扩展与 `.pi/` 配置 | 检查 `workingDirectory(Path.of(...))` |
| 非 Windows 上配置 `pi.cmd` 失败 | 平台不匹配 | macOS / Linux 用 `pi` |

> **建议**：本地开发可以依赖默认值；生产部署（服务、容器、CI）应显式配置绝对路径，不要依赖 `PATH`。

### 启动前做路径体检

```java
try {
    PiCliVersion version = PiCliVersion.detect(config);
    System.out.println(version.semanticVersion().orElse(version.raw()));
} catch (PiProcessException error) {
    // 路径配置错误会在这里暴露，比 PiClient.start() 更早、错误更集中
}
```

`PiCliVersion.detect(config)` 使用与 `PiClient` 完全相同的命令解析逻辑（见下文「CLI 版本探测」），适合在启动客户端前先验证路径与环境。

## 校验规则

- `startupTimeout`、`shutdownTimeout`、`requestTimeout` 必须为正数时长，否则抛 `IllegalArgumentException`。
- `maxJsonLineBytes` 不能小于 1024。
- `maxCapturedStderrChars` 不能为负数。
- `eventBufferCapacity` 必须大于 0。
- `command` 不能为空列表，否则抛 `IllegalArgumentException`。注意 `command` 只校验非空，**不校验可执行文件是否存在**；路径错误会在 `PiClient.start()` 时以 `IOException`（`CreateProcess error=2` 等）暴露。
- 所有对象参数（`executable`、`workingDirectory`、`environment`、`stderrConsumer` 等）为 `null` 时抛 `NullPointerException`。

## 生命周期

```java
PiClient client = PiClient.start(config);
client.onExit().thenAccept(exit -> log.info(
        "PI 退出: code={}, expected={}", exit.exitCode(), exit.expected()));

PiClient replacement = client.restart();
```

- `start(config)` 会启动子进程、执行 `get_state` 就绪探测、启动 stdout/stderr 读取线程和事件分发线程。
- `onExit()` 返回一个 `CompletableFuture<PiProcessExit>`，在子进程退出时完成；`PiProcessExit` 含 `exitCode`、`expected`（是否为预期退出）和 `stderr`。
- `isAlive()` 判断子进程是否存活。
- `stderr()` 返回内存中保留的 stderr 尾部文本（上限由 `maxCapturedStderrChars` 控制）。
- `restart()` 返回新实例，**旧实例的订阅不会复制**，需要重新 `subscribe`。
- `close()` 先关闭 stdin 请求正常终止，超时后（`shutdownTimeout`）强制结束子进程。推荐 try-with-resources：

```java
try (PiClient client = PiClient.start(config)) {
    // ...
}
```

## CLI 版本探测

```java
PiCliVersion version = PiCliVersion.detect(config);
System.out.println(version.semanticVersion().orElse(version.raw()));
```

- `detect(config)` 使用 10 秒超时，`detect(config, timeout)` 可指定。
- 底层执行 `pi --version`，用正则 `(?<!\d)(\d+)\.(\d+)\.(\d+)(?!\d)` 解析语义版本。
- `raw` 保存完整输出；无法解析时 `major/minor/patch` 为 `null`，`semanticVersion()` 返回空。
- SDK 当前验证版本记录在 `PiCliVersion.TESTED_VERSION`（0.84.4），`isTestedVersion()` 可判断。版本不同不一定不兼容，但应运行集成测试。
- 探测失败或超时抛 `PiProcessException`。
