# 会话池与故障恢复

## 为什么需要进程池

问题：RPC 流事件通常没有 prompt 请求 ID。

例子：如果用户 A 和用户 B 同时复用一个 `PiClient`，服务端无法可靠判断文本 delta 属于哪个 HTTP 会话。

解决：每个业务对话使用独立 `PiClient`，由 `PiClientPool` 限制进程总数。

```java
PiClientConfig config = PiClientConfig.builder()
        .workingDirectory(Path.of("D:/workspace"))
        .noSession(true)
        .build();

try (PiClientPool pool = PiClientPool.fromConfig(20, config)) {
    PiClientPool.Entry entry = pool.create();
    PiClient client = entry.client();
    client.prompt("开始分析").settled().join();
    pool.remove(entry.id());
}
```

## 异常退出

```java
client.onExit().thenAccept(exit -> {
    if (!exit.expected()) {
        alert(exit.exitCode(), exit.stderr());
    }
});
```

## 恢复

```java
PiClient recovered = pool.getOrRecover(poolId);
```

替代进程不会自动恢复未落盘上下文，也不会复制旧事件监听器。需要连续上下文时，应启用会话持久化，并在替代客户端中执行 `switchSession()`；监听器必须重新注册。

自动重放最后一个 prompt 不是默认行为，因为旧进程可能已执行部分写文件或 Bash 操作，重放可能造成重复副作用。
